# 안 만들어도 되는 것 사전 (codelazy)

AI는 시키면 다 만든다. 문제는 **안 만들어도 되는 걸 만들 때**다. 이 사전은 부풀기 쉬운 지점을 증상으로 짚고, 표준으로 되돌리는 처방을 준다. ponytail("제일 게으른 시니어처럼")의 정신을 우리 증상 사전 포맷으로 재구현했다.

## 원칙 — 만들기 전에 사다리

코드를 쓰기 전에, 아래 순서로 멈춰 선다:

1. 이거 **진짜 만들어야 하나** (지금 안 쓰면 만들지 않는다, YAGNI)
2. 이미 이 코드베이스에 **있나**
3. **표준 라이브러리**가 하나
4. **한 줄**로 되나
5. 그제야 최소 코드

## 사전을 읽는 법

`menu.json`이 SSOT다. 항목마다:

- `name` — 증상 (사용자가 하려는 과잉설계)
- `aliases` — 같은 요청의 다른 표현
- `culprit` — 무엇을 과하게 만들려 하는가
- `kind` — **direct(즉방형)** 또는 **branch(분기형)**
- `rx` (즉방형) 또는 `branches` (분기형)
- `ask` — 사용자가 복사해 쓰는 요청 문장
- `check` — 덜 만들어졌는지 확인하는 방법
- `before` / `after` — 부풀린 코드와 표준 코드 (실측한 것은 `measured`)

## 유형 규율 — 즉방형과 분기형

**즉방형(direct)**: 표준에 정답이 있는 항목(캐싱→functools.cache, 중복제거→dict.fromkeys). 바로 되돌린다.

**분기형(branch)**: 추상화가 때로 정당한 항목(설정 클래스, 커스텀 예외, 미들웨어, 플러그인). 여기서는 **절대 무조건 "만들지 마"라고 하지 않는다**:

1. `branches`의 갈림길로 지금이 어느 상황인지 **진단**한다
2. 표준으로 될 상황이면 되돌리고, 추상화가 정당한 상황이면 **그렇다고 인정**한다

추상화 자체가 나쁜 게 아니다. **안 시킨, 지금 안 쓰는** 추상화가 부채다. 분기형은 그 경계를 판단한다.

## 모드 1 — 만들기 전 점검

사용자가 "X 만들어줘"라고 하면, 만들기 전에:

1. `aliases`까지 뒤져 해당 항목을 찾는다
2. 즉방형이면 표준 대안을 제시한다 ("그거 functools.cache 한 줄이면 됩니다")
3. 분기형이면 갈림길 질문으로 지금 상황을 먼저 확인한다

## 모드 2 — 코드 리뷰

기존 코드에서 과잉설계를 찾을 때, `culprit`들을 체크리스트로 삼아 스캔하고, 표준으로 되돌릴 수 있는 곳을 `before`/`after`로 제안한다.

## 게으르지 말아야 할 것

덜 만드는 것이 부주의가 되면 안 된다. 다음은 줄이지 않는다:

- 문제 이해 (읽지도 않고 줄이는 건 게으름이 아니라 두 번째 버그)
- 입력 검증·보안·에러 처리
- 명시적으로 요청된 것
- 비자명한 로직의 확인 수단 하나 (실패하면 걸리는 최소 체크)

## 금지

- 분기형 항목에서 진단 없이 "만들지 마"라고 단정하지 않는다
- 정당하게 요청된 것까지 줄이지 않는다
- 표준으로 안 되는 걸 억지로 표준에 욱여넣지 않는다
