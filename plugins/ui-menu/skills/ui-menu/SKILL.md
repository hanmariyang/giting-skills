# UI 메뉴판 (ui-menu)

사용자가 말하는 모호한 UI 표현을 정식 명칭으로 통역하고, 검증된 실물 HTML로 구현을 돕는 사전이다. 8개 코스 105개 항목.

## 데이터 위치 (이 스킬의 플러그인 루트 기준)

- `menu.json` — 사전 SSOT. 카테고리 8개(①페이지 뼈대 ②이동·탐색 ③내용 보여주기 ④입력받는 것 ⑤누르는 것 ⑥알려주는 것 ⑦작은 표시들 ⑧상태·동작)와 항목마다: `id` · `name`(ko/en) · `aliases`(사람이 실제로 하는 말) · `oneliner` · `ask`(그대로 쓰는 요청 문장). 상단 `formula`에 AI한테 시키는 공식이 있다.
- `components/<id>.html` — 항목별 레퍼런스 구현 105종. 전부 자가완결 단일 파일(의존성 0), 접근성 기본 포함.

이 SKILL.md 는 `skills/ui-menu/` 에 있으므로, 플러그인 루트는 두 단계 위다. 먼저 `menu.json` 을 읽어라. 105개 전체가 아니라 필요한 항목만 골라 읽어도 된다(파일이 크면 카테고리·id 로 검색).

## 사용법 4가지

**1. 통역 — 사용자가 UI를 말로 설명할 때**

"위에 눌러서 화면 바뀌는 거" 같은 표현이 오면 `aliases` 와 대조해 항목을 찾는다. 답은 이 형태로:

> 그건 **탭(Tabs)** 입니다. 버튼을 눌러 같은 자리의 내용을 갈아 끼우는 전환 장치예요.
> 다음부터는 이렇게 요청하면 됩니다: "월간·연간 두 개 탭으로 요금표가 전환되게 해줘."

정확한 별칭이 없어도 뜻이 통하면 가장 가까운 항목으로 답한다. 헷갈리는 쌍은 차이를 한 줄로 비교해 고르게 한다:
- "팝업" → 모달(가운데·막음) vs 토스트(구석·저절로 사라짐) vs 팝오버(눌러서 여는 작은 판)
- "옆에서 나오는 거" → 드로어(전체 메뉴 판) vs 사이드바(항상 붙어 있는 것)
- "로딩" → 스피너(끝 모름) vs 프로그레스 바(퍼센트) vs 스켈레톤(자리 뼈대)

**2. 요청 다듬기 — 사용자의 UI 요청이 두루뭉술할 때**

`formula` 의 공식 **[어디에] + [컴포넌트 이름] + [개수] + [세부 조건]** 으로 요청을 다시 써서 확인해 준다.
"FAQ 만들어줘" → "푸터 위 섹션에 아코디언 5개, 처음엔 다 접혀 있고 하나 열면 나머지 닫히게 — 이렇게 진행할까요?"

**3. 구현 — 해당 컴포넌트를 만들어 달라고 할 때**

`components/<id>.html` 을 읽고 그 구조를 레퍼런스로 삼는다. 복붙이 아니라 사용자의 기존 코드 스타일·디자인 토큰에 맞춰 이식한다. 레퍼런스가 지키는 것은 유지한다:

- 시맨틱 요소 우선 (`<dialog>` 로 모달·드로어·라이트박스, `<details name>` 으로 아코디언, checkbox 로 스위치)
- 접근성 최소선 (aria-current, aria-expanded, role, focus-visible, prefers-reduced-motion)
- 의존성 없이 되는 것에 라이브러리를 끌어오지 않는다

**4. 제안 — 무엇을 써야 할지 모를 때**

"이 목록이 너무 길어" → 페이지네이션·더보기·무한 스크롤 중 상황에 맞는 것을 `oneliner` 근거와 함께 2개 이내로 제안한다. 나열하지 말고 고른 이유를 말한다.

## 규칙

- 이름은 반드시 한국어·영어를 함께 준다. 사용자가 다른 도구·다른 AI에게도 그 이름을 쓸 수 있게 하는 것이 목적이다.
- `ask` 문장은 그대로 복사해 쓸 수 있는 형태로 보여준다.
- 사전에 없는 컴포넌트(예: 트리 뷰, 캘린더 히트맵)를 물으면 아는 대로 답하되, 사전에 없는 항목임을 밝힌다.
- 상태(⑧)는 컴포넌트가 아니라 컴포넌트의 국면이다. 버튼 하나를 만들 때도 기본·호버·포커스·디스에이블드를 세트로 챙기라고 권한다.
